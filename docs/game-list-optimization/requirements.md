# Game List Optimization Requirements

## Overview

ปรับปรุงหน้า game list ให้รองรับจำนวนเกมที่เพิ่มขึ้น โดยลดการดาวน์โหลดรูปซ้ำ แสดงสถานะระหว่างรอข้อมูล และยังคงให้ผู้ใช้ค้นหา/กรอง/เรียงรายการเกมได้อย่างต่อเนื่องและเข้าใจได้ชัดเจน โดยไม่รวมการแบ่งหน้าในขอบเขตปัจจุบัน

## User Stories

1. As a ผู้ใช้ ฉันต้องการดูรายการเกมทั้งหมดพร้อมระบบค้นหา/กรอง/เรียงลำดับ เพื่อให้ค้นหาเกมที่ต้องการได้สะดวก
2. As a ผู้ใช้ ฉันต้องการให้รูปภาพเกมโหลดเมื่อใกล้ปรากฏบนหน้าจอ เพื่อให้ไม่ต้องรอดาวน์โหลดรูปภาพทั้งหมดตั้งแต่เริ่มเปิดหน้า
3. As a ผู้ใช้ ฉันต้องการให้รูปภาพที่เคยโหลดแล้วถูกใช้ซ้ำจาก cache เพื่อให้การกลับมาดูรายการเดิมไม่ต้องดาวน์โหลดรูปซ้ำ
4. As a ผู้ใช้ ฉันต้องการเห็น skeleton loading ระหว่างรอข้อมูล เพื่อให้ทราบว่าหน้ากำลังโหลดและไม่เข้าใจว่าหน้าจอค้าง
5. As a ผู้ใช้ ฉันต้องการเห็นสถานะที่ชัดเจนเมื่อไม่มีเกมหรือเกิดข้อผิดพลาด เพื่อให้รู้ว่าควรดำเนินการต่ออย่างไร

## Acceptance Criteria

### User Story 1: รายการและการค้นหา

- 1.1 ระบบต้องแสดงรายการเกมทั้งหมดที่โหลดสำเร็จ พร้อมค้นหา กรอง และเรียงลำดับจากข้อมูลชุดเดียวกัน
- 1.2 หากไม่รองรับ pagination ระบบต้องไม่แสดง pagination control หรือพฤติกรรมแบ่งหน้าที่ทำให้ผู้ใช้เข้าใจผิด
- 1.3 การค้นหา/กรอง/เรียงลำดับต้องไม่ทำให้รายการซ้ำหรือปะปนกัน

### User Story 2: Lazy loading รูปภาพ

- 2.1 รูปภาพเกมที่อยู่นอกพื้นที่มองเห็นและยังไม่ใกล้จะเข้าพื้นที่มองเห็นต้องยังไม่เริ่มดาวน์โหลด
- 2.2 เมื่อรูปภาพเข้าใกล้พื้นที่มองเห็น ระบบต้องเริ่มโหลดรูปโดยอัตโนมัติ
- 2.3 ระหว่างรูปภาพกำลังโหลด ต้องแสดง placeholder หรือพื้นที่สำรองที่มีขนาดคงที่ เพื่อไม่ให้ layout กระโดด
- 2.4 หากรูปภาพโหลดไม่สำเร็จ ต้องแสดง fallback image หรือสถานะรูปเสีย โดยไม่ทำให้รายการเกมหรือหน้าเว็บล้มเหลว
- 2.5 การโหลดรูปภาพต้องไม่บล็อกการแสดงข้อมูลข้อความของการ์ดเกม

### User Story 3: Cache สำหรับรูปภาพ

- 3.1 เมื่อรูปภาพ URL เดิมถูกโหลดสำเร็จแล้ว การแสดงซ้ำใน session เดียวกันต้องสามารถใช้ข้อมูลจาก browser cache หรือ application cache ได้โดยไม่ร้องขอดาวน์โหลดไฟล์ซ้ำโดยไม่จำเป็น
- 3.2 ระบบต้องกำหนดนโยบาย cache ที่เหมาะสมกับรูปภาพที่ URL ไม่เปลี่ยนเมื่อเนื้อหาไม่เปลี่ยน
- 3.3 เมื่อมีการเปลี่ยนเนื้อหารูปภาพ ระบบต้องสามารถทำ cache invalidation ได้ด้วยการเปลี่ยน version/hash ของ URL หรือวิธีที่เทียบเท่า
- 3.4 การ cache รูปภาพต้องไม่ทำให้ข้อมูลเกมหรือรูปภาพของเกมคนละรายการถูกนำมาแสดงปะปนกัน
- 3.5 หาก cache ใช้งานไม่ได้ รูปภาพต้องยังโหลดจากแหล่งข้อมูลหลักได้ และหน้า game list ต้องใช้งานต่อได้

### User Story 4: Skeleton loading

- 4.1 ระหว่างรอข้อมูลหน้าแรก ระบบต้องแสดง skeleton ที่มีโครงสร้างใกล้เคียงกับการ์ดเกมจริง
- 4.2 จำนวน skeleton ต้องสอดคล้องกับจำนวนรายการต่อหน้าหรือพื้นที่แสดงผลที่กำหนด
- 4.3 ระหว่างเปลี่ยนหน้า ระบบต้องแสดงสถานะ loading ที่ชัดเจนและป้องกันการกดเปลี่ยนหน้าซ้ำจนเกิดคำขอซ้อนโดยไม่จำเป็น
- 4.4 เมื่อโหลดข้อมูลสำเร็จ ระบบต้องแทนที่ skeleton ด้วยรายการเกม และต้องไม่เหลือ skeleton ค้างอยู่
- 4.5 เมื่อโหลดข้อมูลล้มเหลว ระบบต้องซ่อน skeleton และแสดงข้อความผิดพลาดพร้อมทางเลือกให้ลองใหม่

### User Story 5: Empty and error states

- 5.1 หากไม่พบเกมตามเงื่อนไข ระบบต้องแสดง empty state ที่เข้าใจได้แทนพื้นที่ว่างเปล่า
- 5.2 หากเกิดข้อผิดพลาดจาก API หรือเครือข่าย ระบบต้องแสดงข้อความแจ้งเตือนที่เหมาะสมโดยไม่แสดงข้อมูลเก่าราวกับเป็นผลลัพธ์ล่าสุด
- 5.3 ปุ่มลองใหม่ต้องเรียกโหลดข้อมูลตามหน้าปัจจุบันและเงื่อนไขล่าสุด โดยไม่ทำให้เกิดรายการซ้ำ

## Scope Notes

- ขอบเขตนี้เน้นการ optimize หน้า game list และรูปภาพที่ใช้ในการ์ดเกม
- รูปภาพมีขนาดเล็กอยู่แล้ว จึงไม่ถือว่าการลดขนาดไฟล์เป็น requirement หลักของงานนี้
- รายละเอียดโครงสร้าง API, component, กลยุทธ์ cache และวิธีตรวจสอบ performance จะกำหนดใน `design.md` ระยะถัดไป
